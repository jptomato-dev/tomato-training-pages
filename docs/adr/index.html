ADR 설계 결정 기록

무엇을 만들지와 어떻게 만들지뿐 아니라, 왜 그 방식을 선택했는지 남깁니다. 가상의 업무관리 시스템 근태관리 사례로 ADR 작성부터 변경 관리, AI 구현과 리뷰까지 연결합니다.

이 페이지의 가상의 업무관리 시스템 설계, Issue 번호, 날짜와 승인 상태는 교육용 가정입니다. 실제 프로젝트의 확정 사항이나 구현 완료를 뜻하지 않습니다.

ADR이란?​

**ADR(Architecture Decision Record)**은 중요한 아키텍처 설계 결정의 배경, 검토한 대안, 선택 이유와 영향을 기록하는 문서입니다. 일본어로는 アーキテクチャ決定記録라고 합니다.

“API 서버 시간을 사용한다”는 결과만 남기면 다음 담당자가 이유를 알기 어렵습니다. ADR은 “왜 PC 시간이나 DB 시간 대신 API 서버 시간을 선택했는가”를 설명합니다. AI 도구나 담당자가 바뀌어도 그 근거를 확인할 수 있습니다.

Issue·Design·OpenAPI와의 차이​

문서·도구주된 질문근태관리 예시
GitHub Issue / 요구사항무엇을 만들고, 언제 완료인가?출퇴근 등록 기능, 수용 조건, 담당자와 진행 상황
ADR왜 이 설계를 선택했는가?API 서버 시각을 선택한 이유와 다른 대안의 한계
Design.md / 상세 설계어떻게 구현하는가?테이블 구조, 처리 순서, 권한 검사, 예외 처리
OpenAPI.yamlAPI의 계약은 무엇인가?경로, 요청·응답 구조, 인증 방식, 오류 응답
Pull Request변경이 기준에 맞고 검증되었는가?설계 및 코드 차이, 테스트 결과, 리뷰와 승인 이력

ADR은 상세 설계서나 API 명세를 대체하지 않습니다. 문서별 역할을 나누고 Issue·ADR·설계·PR을 링크로 연결합니다. 파일 이름과 위치는 기존 프로젝트 규칙을 따릅니다.

가상의 업무관리 시스템: 어느 서버의 시간을 사용할까?​

직원이 출근 버튼을 누르면 시간을 기록한다고 가정합니다. “서버 시간”만으로는 API 서버인지 DB 서버인지, 어느 처리 시점인지 불분명합니다.

선택지장점비용·주의점
A. 사용자 PC 시간기기에서 바로 취득할 수 있음시간 조작·잘못된 시계 설정을 신뢰하게 됨
B. API 서버 시간API 처리 계층에서 기록 기준을 통일여러 서버의 시각 동기화와 오차 관리 필요
C. DB 서버 시간DB 기록의 시각 기준을 통일DB 함수에 따라 트랜잭션 시작·문장 실행 등 시각 의미가 달라질 수 있음

이 사례는 B. API 서버 시간을 선택합니다. 인증·권한 검증 후 등록 로직에서 취득한 시각을 UTC로 저장하고, 화면에는 일본 시간으로 표시한다고 가정합니다. DB 서버 시간도 타당한 선택지가 될 수 있으며 요구사항에 따라 다시 검토할 수 있습니다.

시각의 출처, 저장 기준(UTC), 표시 시간대(Asia/Tokyo), 근무일 판정은 서로 다른 문제입니다. UTC로 저장했다고 야간 근무나 자정 경계의 업무 규칙이 자동으로 정해지지는 않습니다.

실제 ADR Markdown 작성 예제​

프로젝트에서 사용할 파일 경로 예시: docs/adr/ADR-0001-attendance-time.md. 아래 예시는 설계 책임자가 검토하여 승인했다고 가정한 문서입니다. 처음 작성할 때는 Proposed로 시작합니다.

# ADR-0001: 근태 등록 시각의 기준 결정

- 상태: Accepted
- 작성일 / 승인일: 2026-11-23 / 2026-11-23
- 승인 주체: 설계 책임자 (교육용 가정)
- 관련 Issue: #42 출퇴근 등록 기능 (가상 번호)

## 배경 (Context)
직원 PC 시간을 신뢰하면 기기 설정이나 시간 조작 때문에
출퇴근 기록이 부정확해질 수 있다.
온라인 등록을 대상으로, API가 요청을 처리하는 시각을 기록한다.

## 검토한 대안 (Options)
- A. 클라이언트 PC 시간: 구현은 쉽지만 사용자가 변경할 수 있다.
- B. API 서버 시간: 처리 계층에서 기준을 통일하지만 시각 동기화가 필요하다.
- C. DB 서버 시간: DB 기준을 통일하지만 DB 함수와 트랜잭션 시각 의미에 의존한다.

## 결정 (Decision)
인증·권한 검증을 통과한 요청에 대해, 등록 로직에서 API 서버 시각을
한 번 취득하여 출퇴근 시각으로 사용한다.
클라이언트가 보낸 시각은 공식 출퇴근 시각으로 채택하지 않는다.
DB에는 UTC 기준의 시점으로 저장하고 화면에는 Asia/Tokyo로 변환해 표시한다.

## 결정 이유 (Rationale)
클라이언트 시계의 영향을 배제하고, API 처리 시점의 의미를 명확히 한다.
DB 시각도 유효한 대안이지만, 이 사례는 API 처리 계층에서 시각을
결정하고 테스트에서 시계를 대체할 수 있는 구조를 선택한다.

## 영향 (Consequences)
- API 서버 간 시각 동기화와 시계 오차 모니터링이 필요하다.
- 네트워크 지연 때문에 버튼을 누른 실제 시각과 기록 시각이 다를 수 있다.
- UTC 저장과 일본 시간 표시의 변환 테스트가 필요하다.
- 이 결정만으로 중복 요청이나 다른 직원의 기록 변경을 방지하지는 못한다.

## 범위 밖 / 미결사항
- 근무일 경계, 야간 근무, 자정 이후 퇴근의 귀속일
- 오프라인 등록, 시각 정정 및 승인 절차
이 항목은 담당자가 별도로 결정하며 AI가 임의로 보완하지 않는다.

## 검증 기준
- PC 시각을 변경해도 서버의 기준 시각으로 등록된다.
- 고정된 테스트 시계를 주입해 출퇴근 기록 시각을 검증한다.
- UTC 시점이 일본 시간으로 올바르게 표시된다.
- 근무일 판정 테스트는 별도 정책 확정 후 추가한다.

ADR 번호는 결정 기록의 식별자입니다. Issue #42와 번호를 맞출 필요가 없으며, 한 Issue에 여러 ADR이 연결될 수 있습니다.

상태와 변경 이력 관리​

상태의미운영 방법
Proposed · 검토 중대안과 결정안을 논의하는 단계확정된 구현 기준으로 취급하지 않고 책임자 검토를 요청
Accepted · 승인합의된 결정승인자·일자·검토 PR을 남기고 구현·리뷰 기준으로 사용
Superseded · 대체됨새로 승인된 ADR이 기존 결정을 대체기존 근거를 보존하고 후속 ADR과 양방향으로 연결

예를 들어 API 서버 시간에서 DB 서버 시간으로 바꿀 때는 새 ADR-0015에 변경 배경, 대안, 데이터·테스트·운영 영향을 적습니다. 새 문서가 Proposed인 동안 기존 Accepted 결정은 유효합니다.

  • 새 ADR을 Proposed로 작성하고 기존 ADR을 참조합니다.

  • 설계 책임자가 검토·승인하면 새 ADR을 Accepted로 바꾸고, 기존 ADR을 Superseded로 표시합니다.

  • 기존 문서에는 Superseded by ADR-0015, 새 문서에는 Supersedes ADR-0001과 실제 파일 링크를 기록합니다.

  • 같은 변경에서 DECISIONS.md 요약과 관련 설계·OpenAPI를 정합하게 갱신하고, 코드·테스트·전환 작업을 PR로 추적합니다.

승인된 결정의 의미를 조용히 덮어쓰거나 과거 ADR을 삭제하지 않습니다. 오탈자나 링크 수정은 기존 파일에서 처리하되 Git 이력을 남깁니다. 결정 변경은 새 ADR로 남기며 번호를 재사용하지 않습니다. 승인과 실제 배포 완료도 구분하여 기록합니다.

언제 ADR을 작성할까?​

여러 기능에 영향을 주거나, 되돌리는 비용이 크거나, 미래의 개발자가 선택 이유를 알아야 하는 결정을 대상으로 합니다. 하나의 ADR은 하나의 중요한 결정에 집중합니다.

결정 예시권장 기록 위치이유
인증 서버를 Keycloak으로 통일ADR보안 경계와 여러 서비스에 영향
시각 출처·UTC 저장·시간대 정책ADR데이터 해석과 서비스 간 일관성에 영향
여러 프로젝트의 근무시간 배분 모델ADR업무 규칙과 데이터 모델 변경 비용이 큼
기존 규칙에 따른 버튼 색상·문구 수정Issue / 디자인 규칙 / PR작은 변경마다 별도 ADR을 만들 필요 없음
단순 변수명 변경PR일반적으로 장기적인 설계 근거가 필요하지 않음

작성 전에는 기존 ADR과 DECISIONS.md를 먼저 찾습니다. 배경, 대안, 선택 이유, 부정적인 영향, 미결사항과 검증 방법을 짧고 명확하게 적습니다. 작은 UI 변경이라도 접근성 정책처럼 범위가 커지면 ADR 필요성을 다시 판단합니다.

DECISIONS.md와 중복 없이 연결하기​

하네스 표준 템플릿의 docs/DECISIONS.md는 작은 프로젝트에서는 결정 본문까지 기록할 수 있습니다. 중요한 결정이 늘어나면 목차·요약은 DECISIONS.md, 자세한 근거는 개별 ADR로 나눕니다. 기존 본문을 ADR로 옮겼다면 원래 위치에는 요약과 링크만 남깁니다.

docs/
├── SPEC.md
├── ARCHITECTURE.md
├── DECISIONS.md              # 현재 결정 요약·상태·ADR 링크
├── design/
│   └── attendance-design.md  # 상세 설계 (예시)
└── adr/
    └── ADR-0001-attendance-time.md
openapi/
└── openapi.yaml              # API 계약 (예시)

docs/DECISIONS.md에 넣을 목차 예시입니다.

# 설계 결정 목록

| ADR | 상태 | 결정 요약 |
| --- | --- | --- |
| [ADR-0001](adr/ADR-0001-attendance-time.md) | Accepted | API 서버 시각 사용, UTC 저장 |

상세한 배경·대안·영향은 연결된 ADR을 기준으로 확인한다.
대체된 결정은 삭제하지 않고 Superseded 상태와 후속 ADR 링크를 남긴다.

이 구조는 실제 개발 프로젝트에 적용할 예시입니다. 교육자료 저장소에 같은 내용의 DECISIONS.md나 실제 프로젝트용 ADR을 중복 생성하지 않습니다. 이미 docs/decisions/ 등을 사용 중이면 그 위치를 유지합니다.

AI 주도 개발 프로세스에 연결하기​

Issue → ADR(필요한 경우) → 상세 설계·OpenAPI → AI 구현
      → Pull Request → 자동 테스트·리뷰 → 병합

  • Issue: 출퇴근 등록 목적과 수용 조건을 정하고, 미정인 업무 규칙을 구분합니다.

  • 설계: ADR로 대안을 검토하고 사람이 결정을 승인합니다. 상세 설계와 API 계약에 반영합니다.

  • AI 구현: AGENTS.md와 관련 Accepted ADR, 요구사항, 설계를 읽도록 명시합니다. 충돌·미결사항은 보고하게 합니다.

  • PR: 관련 Issue·ADR과 변경 파일, 검증 결과, 남은 문제를 적습니다.

  • 자동 테스트·리뷰: 코드가 수용 조건과 ADR을 지키는지 확인합니다. 자동 테스트는 프로젝트에 구성되어 있어야 실행됩니다.

  • 병합: 검토와 검증을 마친 변경을 반영합니다. 배포가 별도라면 전환·배포 완료를 따로 추적합니다.

AI에게 전달할 요청 예시​

가상의 Issue #42 출퇴근 등록 기능을 구현해 주세요.

먼저 AGENTS.md, docs/DECISIONS.md와 연결된 Accepted ADR,
요구사항, 상세 설계, OpenAPI를 읽어 주세요.
ADR-0001의 API 서버 시각·UTC 저장 결정을 따르세요.
Proposed 또는 Superseded ADR을 현재 확정 기준으로 사용하지 마세요.
근무일 경계 등 미결사항과 문서 간 충돌은 질문으로 정리하세요.
기존 결정을 바꿔야 한다면 근거와 ADR 변경안을 먼저 제시하세요.
변경 파일, 실행한 테스트와 결과, 남은 문제를 보고해 주세요.

리뷰에서 확인할 항목​

  • 클라이언트 시각을 그대로 저장하지 않는가?

  • 시각 취득 시점과 UTC 저장·화면 표시가 결정과 일치하는가?

  • 다른 직원의 기록 변경 방지와 중복 요청 처리는 별도 요구사항대로 검증했는가?

  • 야간 근무·근무일 경계를 AI가 임의로 확정하지 않았는가?

  • 설계가 바뀌었다면 ADR, 요약, 상세 설계, 구현·테스트가 함께 갱신되었는가?

ADR은 AI에게 판단 근거를 제공하지만 준수를 자동으로 보장하지는 않습니다. 테스트와 사람의 최종 검토가 필요하며, 도구를 바꿀 때는 tasks/CURRENT.md에 관련 ADR과 검증 결과를 함께 인계합니다.
