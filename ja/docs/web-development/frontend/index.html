フロントエンド

Webアプリケーションの画面設計と実装を学ぶ開発者・PM向けの教材です。HTML/CSSとSPAの基礎知識があると理解しやすくなります。

画面デザイン（UI/UX）​

UIは利用者が接する画面と操作要素、UXは業務を遂行する際の体験全体です。業務システムでは見た目だけでなく、検索効率、入力ミス防止、アクセシビリティ、権限に応じた表示、大量データの処理、一貫性が重要です。

成果物目的
ワイヤーフレーム項目・ボタンの配置と情報構造
モックアップ色、書体、余白を含む視覚設計
プロトタイプ画面遷移と操作の確認
デザインシステムトークン、コンポーネント、利用ルールの共通体系
実装コード実データ、権限、例外処理、テストを含む製品

優先的に検討するAI・デザインツール​

ツール強み注意点
Google Stitch自然言語による複数案の探索とコード・デザイン成果物の活用出力形式、Figma連携、DESIGN.mdの対応範囲を利用環境で確認
Figma Design詳細設計、変数、再利用コンポーネント、共同レビュー学習コスト、編集権限、料金
Figma Make動作するAIプロトタイプでの画面検討生成コードの技術スタック・セキュリティ要件を別途検証

Visily / Uizardスクリーンショット・スケッチ等による初期構想詳細編集やエクスポートの制約
Penpotオープンソース・セルフホスト運用負荷、AI連携方式
Lovable / Bolt / Replit動作するアプリの迅速な試作データ保存、認証、依存関係、デプロイ費用

汎用AIは要件や画面構造の検討に、コーディングエージェントは既存コードと共通コンポーネントを使った実装に適しています。客観的な製品ランキングではなく、同じ要件で比較することを推奨します。

FigmaとAIのMCP連携​

MCP（Model Context Protocol）はAIが外部ツールやコンテキストにアクセスするための標準インターフェースです。Figma MCPを利用すると、対応クライアントからデザイン構造、変数、レイアウト等を実装に活用できます。

Figmaデザイン → Figma MCP → Codex / Copilot / Claude Code
                           ↓
                   Angular / TypeScript / CSS
                           ↓
                    GitHub PR / テスト / レビュー
  1. Figma MCP公式ドキュメントでクライアント別の接続方法と権限を確認します。
  2. デザインリンクまたはノードを指定し、既存UIライブラリとリポジトリのルールをAIに伝えます。
  3. 実装済みコンポーネントの再利用を指示し、生成コードとデザインを比較します。
  4. アクセシビリティ、レスポンシブ表示、状態別UI、テストを確認してPRで管理します。

MCPは完全なコード変換や全クライアントでのデザイン書き込み権限を保証するものではありません。読み書き機能、認証、料金制限は公式文書と組織ポリシーで確認します。

Angular UIコンポーネントとデザインシステム​

ツール特徴
PrimeNGテーブル、フィルター、ツリー、フォームなど業務画面向け
Angular MaterialMaterial Designに基づく一貫したUI
NG-ZORROAnt Designベースの企業向けAngularコンポーネント
AG Grid複雑なデータグリッド。一部高度な機能は有料
Storybook共通コンポーネントの状態別確認、文書化、テスト
Playwright実ブラウザーの操作・回帰テスト

React向けMUIやAnt Designも参考になりますが、AngularではAngular対応ライブラリを選びます。基本ライブラリを一つ選び、必要に応じて特殊コンポーネントを追加することを推奨します。

共通デザインルールには色（ブランド、主要操作、成功、警告、エラー）、書体・サイズ、余白（例：4/8/12/16/24/32px）、ボタン、入力フォーム、テーブル、状態表示、キーボード操作、フォーカスを含めます。日本語業務画面ではNoto Sans JPを候補とし、エラーや承認状態は色だけでなく文言でも示します。これは教材上の例であり、特定プロジェクトの確定仕様ではありません。

推奨ワークフロー​

工程成果物・ツール
1. 画面要件ChatGPT等で役割、項目、操作、受入基準を整理しIssue登録
2. 共通デザインFigma変数・コンポーネント、UIライブラリ、DESIGN.md
3. AIデザイン案Stitch等で複数案を比較
4. 詳細設計Figma Design / Makeで配置と遷移を検討
5. 業務レビュー担当者が代表シナリオを操作して確認
6. 実装VS Code + Codex/Copilot等、必要に応じてFigma MCP
7. 検証Storybook、Playwright、アクセシビリティ、レスポンシブ確認
8. 変更管理GitHub PR、CI、人によるレビュー後にマージ

小規模チームではFigmaを使わず、UIライブラリとAIコーディングで直接試作する方法もあります。画面数が多い場合や業務担当者との合意が必要な場合は、設計と実装を分けることで手戻りを抑えやすくなります。

実習：架空の社員一覧画面​

目標は業務画面の検索、一覧表示、権限別操作を設計することです。以下は概念実習であり、実際のツールで動作検証済みではありません。

  • 入力：所属部署、社員名、在籍状態
  • 一覧：社員番号、氏名、部署、状態、詳細ボタン
  • 状態：初期ロード、検索結果なし、APIエラー、権限なし
  • 操作：検索、クリア、ページ移動、詳細表示
  • 受入基準：キーボード操作可能、結果なしとエラーを区別、権限外の変更要求はサーバーで拒否

AIへの指示例：

日本語の業務用社員一覧画面のデザイン案を作成してください。
左側メニュー、上部検索フィルター、データテーブルを用い、
Angular + PrimeNGで実装可能なコンポーネントで構成してください。
ローディング・結果なし・エラー・権限なしの状態と
キーボード操作を考慮し、架空データとデザインルールを提示してください。

案を比較しFigmaまたはコードで修正し、Storybookで各状態を確認、Playwrightで検索とエラー表示を検証します。ボタンを非表示にするだけでは認可を実装できません。

デザイン資料とソースコードの管理​

docs/design/
  DESIGN.md
  DESIGN_SYSTEM.md
  UI_GUIDELINES.md
  COMPONENT_CATALOG.md
  SCREEN_LIST.md
  SCREEN_TRANSITIONS.md
  screens/
    employee.md

最初はDESIGN.md一つで始め、必要に応じて分割します。Figmaを視覚設計、GitHubを業務ルール・設計判断・コードの原本とする方法があります。同じデザイントークンを双方で独立して変更しないよう同期責任を定めます。関連する設計方法はAI設計を参照してください。

デザイン参考サイト​

Mobbinは実サービス事例、DribbbleとBehanceはデザイン案、Figma CommunityはUIキット、SakaiとTablerは管理画面の参考資料です。テンプレートのライセンスと利用技術を確認します。

学習順序と推奨構成​

Google Stitch → Figma Design → Figma Make → Figma MCP → PrimeNG → Storybookの順で実習し、v0とPenpotを比較対象にすることを推奨します。業務システムではStitch + Figma + AIコーディング + Angular UIライブラリ + Storybook/Playwright + GitHubが実用的な選択肢の一つです。
