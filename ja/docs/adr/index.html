ADR（アーキテクチャ決定記録）

何をどのように作るかだけでなく、なぜその方式を選んだかを記録します。架空の業務管理システムの勤怠管理を例に、ADRの作成・変更管理・AIによる実装とレビューの関係を解説します。

教材の仮定

このページの架空の業務管理システム設計、Issue番号、日付、承認状態は教材用の例です。実際のプロジェクトで承認・実装された事実ではありません。

ADRとは？​

**ADR（Architecture Decision Record）**は、重要な設計判断の背景、検討した代替案、選択理由、影響を残す文書です。

「APIサーバーの時刻を使用する」という結論だけでは、後任者は理由がわかりません。ADRは「PCやDBの時刻ではなく、なぜAPIサーバーの時刻を選んだか」を説明します。AIツールや担当者が変わっても判断根拠を参照できます。

Issue・Design・OpenAPIとの違い​

文書・ツール主な問い勤怠管理の例
GitHub Issue / 要件何を作り、いつ完了とするか出退勤登録、受け入れ条件、進捗
ADRなぜその設計を選んだかAPI時刻の選択理由と他案の問題
Design.md / 詳細設計どう実装するかテーブル、処理順序、認可、例外
OpenAPI.yamlAPIの契約は何かパス、要求・応答、認証、エラー
Pull Request基準に合うか、検証済みか設計・コードのDiffとレビュー

ADRは詳細設計書やAPI仕様の代わりではありません。各文書を役割ごとに分け、相互リンクでつなぎます。既存プロジェクトのファイル命名規則を優先してください。

架空の業務管理システム：どのサーバーの時刻を使うか？​

社員が出勤ボタンを押した場合、どの時刻を記録すべきでしょうか。「サーバー時刻」だけではAPIなのかDBなのか、取得タイミングも不明瞭です。

選択肢利点留意点
A. 利用者PCの時刻端末から直接取得可能時刻の改ざんや誤設定の影響
B. APIサーバーの時刻API処理層で基準を統一サーバー間の時刻同期と誤差管理
C. DBサーバーの時刻DBの記録基準を統一DB関数によってトランザクション開始・実行時刻の意味が異なる

この教材ではB. APIサーバーの時刻を選択します。認証・認可の確認後に登録ロジックで時刻を取得し、UTCで保存して画面には日本時間を表示する想定です。DB時刻も妥当な代替案であり、要件次第で再検討できます。

時刻の取得元、保存基準（UTC）、表示タイムゾーン（Asia/Tokyo）、勤務日の判定は別の問題です。UTCで保存しただけで夜勤や日付をまたぐ勤務の業務規則が決まるわけではありません。

ADR Markdownの記載例​

パス例：docs/adr/ADR-0001-attendance-time.md。以下は設計責任者がレビューして承認したと仮定した文書です。新規作成時はProposedから開始します。

# ADR-0001: 勤怠登録時刻の基準

- 状態: Accepted（教材の仮定）
- 作成日 / 承認日: 2026-11-23 / 2026-11-23（例）
- 承認者: 設計責任者（例）
- 関連Issue: #42 出退勤登録機能（架空番号）

## 背景（Context）
社員PCの時刻を信頼すると、端末の設定ミスや改ざんで
出退勤記録が不正確になる可能性がある。
オンライン登録時にAPIが要求を処理する時刻を記録する。

## 代替案（Options）
- A. クライアントPC：実装は容易だが変更可能
- B. APIサーバー：処理層で統一できるが時刻同期が必要
- C. DBサーバー：DB側で統一できるが関数とトランザクションの意味に依存

## 決定（Decision）
認証・認可を通過した要求について、登録ロジックで
APIサーバー時刻を一度だけ取得し、出退勤時刻とする。
クライアントから送信された時刻を正式な時刻に採用しない。
DBにはUTCで保存し、画面ではAsia/Tokyoに変換して表示する。

## 理由（Rationale）
クライアントの時計への依存を避け、API処理時点の意味を明確にする。
DB時刻も有効な代替案だが、この例ではAPI処理層で時刻を決定し、
テスト時に時計を置き換えられる構造を採用する。

## 影響（Consequences）
- APIサーバー間の時刻同期・誤差監視が必要
- ネットワーク遅延によりボタン押下時刻と記録時刻がずれる
- UTC保存と日本時間表示の変換テストが必要
- 重複要求や他社員の記録変更をこの決定だけで防ぐことはできない

## 対象外・未決定
- 勤務日の境界、夜勤、日付をまたぐ退勤の帰属
- オフライン登録、時刻修正、承認の手順
AIが勝手に業務ルールを補ってはならない。

## 検証
- PC時刻を変更してもサーバー基準で登録される
- 固定したテスト時計で出退勤記録を検証する
- UTC時刻が正しく日本時間に表示される
- 勤務日の判定は別途方針を決定してからテストする

ADR番号は設計判断の識別子です。Issue番号と合わせる必要はなく、1つのIssueから複数のADRを作る場合もあります。

ステータスと変更履歴の管理​

状態意味運用
Proposed（検討中）代替案と方針を議論中確定した実装基準にしない
Accepted（承認）合意・承認された判断承認者、日付、PRを記録して実装・レビュー基準に
Superseded（置き換え）新たに承認したADRで代替旧文書を残し、後続ADRと相互リンク

例えばAPI時刻からDB時刻に変更する場合、新たなADR-0015に背景、代替案、データ・テスト・運用への影響を記載します。新ADRがProposedである間は、以前のAcceptedが有効です。

  1. 新ADRをProposedで書き、旧ADRを参照します。
  2. 設計責任者の承認後、新ADRをAccepted、旧ADRをSupersededにします。
  3. 旧文書にSuperseded by ADR-0015、新文書にSupersedes ADR-0001と実際のリンクを記載します。
  4. DECISIONS.mdの要約、詳細設計、OpenAPIを整合させ、実装・テスト・移行をPRで追跡します。

承認された判断の意味を黙って書き換えたり、過去ADRを削除してはいけません。誤字やリンクの修正は既存ファイルで行い、Git履歴を残します。判断の変更は新ADRとして記録し、番号を再利用しません。承認と本番反映完了も区別します。

ADRを作成する判断基準​

複数機能に影響する、元に戻すコストが高い、後の開発者が判断理由を知る必要がある場合に作成します。原則として1つのADRにつき1つの重要な決定に集中します。

判断例記録場所理由
共通認証サーバーにKeycloakを採用ADRセキュリティ境界や複数サービスに影響
時刻の取得元・UTC保存・表示タイムゾーンADRデータ解釈とシステム間整合性に影響
複数案件への勤務時間配分モデルADR業務ルール・データモデル変更が高コスト
既存規則に沿ったボタン色・文言の変更Issue / デザイン規則 / PR小変更に個別ADRは不要
単純な変数名変更PR長期的な設計根拠が通常不要

作成前には既存のADRとDECISIONS.mdを探します。背景、代替案、選択理由、不利益、未決定事項、検証方法を簡潔に書きます。小さなUI変更でもアクセシビリティ方針のように範囲が広がる場合は見直します。

DECISIONS.mdと重複させずに連携する​

ハーネス標準テンプレートのdocs/DECISIONS.mdは、小規模なプロジェクトでは決定の本文まで記録できます。判断が増えたら一覧・要約はDECISIONS.md、詳しい根拠は個別ADRと分けます。移動済みの本文は重複させず、元の場所には概要とリンクだけ残します。

docs/
├── SPEC.md
├── ARCHITECTURE.md
├── DECISIONS.md              # 決定一覧・状態・ADRリンク
├── design/
│   └── attendance-design.md  # 詳細設計の例
└── adr/
    └── ADR-0001-attendance-time.md
openapi/
└── openapi.yaml              # API契約の例

docs/DECISIONS.mdに置く一覧例です。

# 設計判断一覧

| ADR | 状態 | 要約 |
| --- | --- | --- |
| [ADR-0001](adr/ADR-0001-attendance-time.md) | Accepted | API時刻、UTC保存 |

詳しい背景・代替案・影響はリンク先のADRを参照する。
置き換えた判断は削除せず、Supersededと新ADRをリンクする。

これは実際の開発プロジェクトに適用する例です。教育資料用の保存場所に同じ決定を二重作成しません。既存のdocs/decisions/などの命名規則がある場合はそれを維持します。

AI主導開発の流れに組み込む​

Issue → ADR（必要時） → 詳細設計・OpenAPI → AI実装
      → Pull Request → 自動テスト・レビュー → マージ
  1. Issue： 出退勤登録の目的と受け入れ条件を定め、未決定の業務規則を分けます。
  2. 設計： ADRで代替案を検討し、人が承認してから詳細設計・API契約へ反映します。
  3. AI実装： AGENTS.md、Accepted ADR、要件、設計を参照させ、相違や未決定事項を報告させます。
  4. PR： 関連Issue・ADR、変更ファイル、検証結果、残課題を明記します。
  5. テスト・レビュー： 基準に沿うかを検証します。自動テストは設定済みの場合のみ実行されます。
  6. マージ： 検証済みの変更を取り込みます。デプロイが別工程なら完了状況も分けて追跡します。

AIへの依頼例​

教材上のIssue #42 出退勤登録を実装してください。

AGENTS.md、docs/DECISIONS.md、リンク先のAccepted ADR、
要件、詳細設計、OpenAPIを最初に読んでください。
ADR-0001のAPIサーバー時刻・UTC保存の判断に従ってください。
Proposed/Superseded ADRを確定基準としないでください。
勤務日の境界など未決定の規則と文書の食い違いは報告してください。
変更する場合は理由と新ADR案を先に提示してください。
変更ファイル、テスト結果、残課題を報告してください。

レビュー項目​

  • クライアント時刻をそのまま保存していないか
  • 時刻取得とUTC保存・表示の変換が決定に一致しているか
  • 他社員の記録変更や重複要求への対策を別要件で検証したか
  • AIが夜勤・勤務日の境界を勝手に決めていないか
  • 判断が変わった場合にADR・一覧・詳細設計・コード・テストを合わせて更新したか

ADRはAIへ判断根拠を渡しますが、準拠を自動保証しません。テストと人の最終レビューが必要です。ツールの引き継ぎ時はtasks/CURRENT.mdに関連ADRと検証結果を記録します。
